# Assignment: Creativity Tool

## Make a Tool That Has a Point of View

For this assignment, you will create a **Creativity Tool**: custom software that gives someone a new way to make, manipulate, discover, understand, perform, compose, design, transform, or think.

The world does not particularly need another general-purpose drawing program, image editor, note-taking app, or productivity tool. Instead, you are encouraged to make software that is niche, opinionated, and experimental. Your tool might be useful, but utility is not the primary goal. It might serve a tiny audience, an obscure practice, a peculiar aesthetic, or one specific person. It might embody an idea that sounds questionable until somebody actually tries it.

Can a tool be an artwork? Yes — but a tool is different from an artwork that simply presents itself to an audience. **A tool gives some of its agency away.** It establishes a set of possibilities and invites another person to act within them. This makes tool-building an interesting form of artistic practice. Instead of asking:

> **What can I make?**

you are asking:

> **What can I make possible for someone else?**

A good creativity tool can be a small intervention. It does not need to compete with Photoshop, Blender, Ableton, Illustrator, or any other general-purpose application. In fact, it may be better if it does something extremely specific.

> **Would anyone actually want to use this? Let's find out by making it.**

Robin Sloan has described small, personally made software with the analogy that **“an app can be a home-cooked meal.”** Software does not have to be a product for thousands or millions of customers. It can be made for a particular community, a peculiar situation, or even **one specific person**.

At the same time, AI-assisted programming has made it extraordinarily easy to produce software that nobody particularly needs. There is now an enormous quantity of [slopware: competent-looking, generic, disposable software](https://www.nytimes.com/2026/07/20/technology/apple-app-store-vibecoding.html). Your challenge is therefore **not simply to make an app,** but to have a point of view about **what would be interesting for software to make possible**.

---

## The Assignment

Design and build a custom **Creativity Tool**. Your tool should expand, augment, complicate, simplify, question, undermine, improve, or otherwise alter some creative activity.

It might be a tool for:

* drawing, typography, photography, animation, sound, video, performance, fabrication, writing, mapping, visualization, or physical computing;
* transforming one kind of media into another;
* examining or interpreting an existing media file in an unusual way;
* collaborating with another person;
* imposing an interesting constraint;
* making an inaccessible technique accessible;
* exposing some normally invisible property of a medium;
* preparing files for a particular machine or fabrication process;
* doing something extremely specific that existing software does badly;
* doing something that nobody has previously thought was worth making software for.

The result could be useful, absurd, critical, poetic, specialized, provocative, or some combination of these. But it should enable **an action**, not merely display an effect.

---

## Start With a Person and a Possibility

Before thinking about features, consider:

**Who is this for?**

“The general public” is not a useful answer.

Perhaps your tool is for:

* yourself
* your roommate;
* your grandmother;
* tattoo artists;
* people who own pen plotters;
* someone with only one free hand;
* musicians who cannot read notation;
* people making protest signs;
* children learning embroidery;
* your classmates using the laser cutter;
* a particular friend with one particular obsession.

Then ask:

> **What can this person do after my tool exists that they could not easily do before?**

That sentence should be reasonably easy to complete.

---

## Tools as Provocations

Tools are not neutral.

Every tool contains assumptions about what its users might want to do. A pencil, camera, spreadsheet, sampler, Photoshop filter, search engine, or laser cutter does not merely facilitate activity; it also proposes certain kinds of activity.

Making a tool is therefore a way of making an argument.

Your argument might be:

> People should be able to draw collaboratively without seeing each other's marks.

> A color palette should be derived from the places where you spend your time.

> A photograph should be editable according to its depth rather than its pixels.

> Anyone should be able to turn their handwriting into something a pen plotter can perform.

> A person should be able to design a pair of disposable shoes around the exact shape of their feet.

The software is the implementation of the proposition.

---

## Inputs and Outputs

Your project must participate in the larger ecosystem of creative media.

**It cannot be a sealed box.**

Your tool must **import and/or export media using an open, documented file format.**

For example, it might:

* export SVG for a laser cutter or pen plotter;
* export PNG, JPEG, GIF, WebP, or an image sequence;
* import an image and generate an analysis of it;
* import audio and visualize or transform it;
* export MIDI;
* generate an STL or OBJ;
* import or export CSV or JSON;
* create a GPL palette file;
* transform one open media format into another.

At minimum, the user must be able to **get something out of the tool**, or use the tool to **see, understand, interpret, or manipulate something they brought into it**.

A screenshot of your interface does not count as an export mechanism.

Prefer open, interoperable formats over proprietary ones. Think about what could happen to the output **after it leaves your software**.

---

## Scope

You have approximately **1.5 weeks**.

This is intentionally a short development period. You are encouraged to use AI-assisted programming extensively. You are not being evaluated on your ability to type every line of code yourself.

This means that **technical ambition is cheap** in a way that it was not a few years ago.

Do not mistake complexity for quality.

A small tool with a strange, precise, well-considered purpose is preferable to a sprawling application containing fifteen half-developed features.

Use AI to help you implement your idea. **Do not outsource the idea itself.**

You remain responsible for deciding:

* what the tool is for;
* whom it is for;
* what assumptions it makes;
* what interactions are important;
* what should be removed;
* what constitutes good output;
* whether the software actually works;
* whether what you have made is worth using.

---

## Some Questions to Consider

What creative act is your tool intervening in?

What does existing software assume about that activity?

What happens if you challenge one of those assumptions?

Could your software be designed for exactly one person?

Could it be designed around a particular machine, place, collection, material, disability, habit, ritual, or community?

Could it connect two things that currently require an annoying sequence of manual steps?

Could it make an expert technique available to a novice?

Could it deliberately make an easy activity more difficult?

Could it reveal information that is present in a media file but normally difficult to perceive?

Could its output become the input to another tool?

Could your tool create a new creative practice rather than merely accelerate an existing one?

And most importantly:

> **What becomes possible because this tool exists?**

# Requirements

Your project must:

1. **Be a custom software tool for creative activity.**

2. **Have an intended user.**
   This may be a broad community, a narrow community, or one specific person.

3. **Have a clear proposition.**
   You should be able to explain what your software allows its user to do that was previously difficult, impossible, inaccessible, tedious, or simply unimagined.

4. **Accept and/or produce media in an open file format.**
   The project must meaningfully import, analyze, transform, visualize, or export media.

5. **Actually work.**
   A narrow, functioning tool is preferable to an ambitious mockup.

6. **Be published as a working web application.** Recommended locations to host your application include [github.io](https://docs.github.com/en/pages), [websim.com](https://websim.com/blog/what-is-websim), [itch.io](https://itch.io/tools).
   Someone with the URL should be able to use your project without installing your development environment.

7. **Have its source code published in a GitHub repository.**

---

# Deliverables

Submit a project page containing:

* a link to the working `github.io` application;
* a link to its GitHub repository;
* a concise description of **what the tool allows someone to do**;
* an identification of its intended user or users;
* several examples of input/output produced with the tool;
* screenshots or other documentation showing the tool in use;
* a brief discussion of how you used AI-assisted programming, including something the AI got wrong, misunderstood, or implemented badly;
* a brief reflection on what you would change or develop further if you had another week.

You will also **demonstrate the tool live in class**.

Come prepared to show us not only the interface, but an actual use of the tool: put something into it, do something with it, and show us what comes out.

---

# Evaluation

Projects will be evaluated primarily on:

**Concept** — Does the tool have a specific and interesting proposition?

**Empowerment** — Does it genuinely give its user some new capability, perspective, or way of working?

**Specificity** — Does it feel designed for an actual purpose or person, rather than like a generic demonstration?

**Interaction** — Are the controls, constraints, and feedback appropriate to what the tool is trying to accomplish?

**Output** — Does the tool produce, transform, reveal, or interpret something meaningful?

**Execution** — Does it work reliably enough to be used?

**Judgment** — Did you make good decisions about what to build, what not to build, and what to delegate to AI?

The sophistication of the underlying code is **not** itself a criterion.

The question is not:

> *How impressive is this software?*

It is:

> **What does this software make possible?**
